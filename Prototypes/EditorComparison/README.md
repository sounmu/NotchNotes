# NotchNotes Editor Lab

TextKit 2 기반의 현재 편집기와 **Milkdown Crepe 7.23.0 + WKWebView**를 비교하는 독립 시제품입니다. 현재 저장소의 MarkdownEngine을 직접 연결합니다.

## 실측 결과 · 2026-11-05

이 Mac(arm64, RAM 18GiB, macOS 27.0.1)에서 각 조건 3회의 중앙값입니다. 메모리는 앱 + 관측된 WebKit 보조 프로세스의 **physical footprint** 합계입니다.

| 문서 | Native 메모리 | Crepe 메모리 | Native 준비 신호 | Crepe 준비 신호 |
|---|---:|---:|---:|---:|
| 짧은 메모 (280 UTF-16) | 24.4MiB | 115.6MiB | 198ms | 616ms |
| 1만 자 (10,062 UTF-16) | 28.3MiB | 141.0MiB | 258ms | 603ms |
| 5만 자 (50,066 UTF-16) | 31.8MiB | 199.0MiB | 574ms | 659ms |

- Crepe 메모리 범위: 짧은 메모 **114.5–221.3MiB**, 1만 자 **139.6–237.2MiB**, 5만 자 **188.4–200.3MiB**. WebKit GPU 프로세스의 footprint 변동도 합산에 반영했습니다.
- 대기 CPU는 두 편집기 모두 낮았습니다. 조건별 중앙값은 코어 하나 기준 **0.001–0.059%**, 전체 유효 실행 중 최대 **0.123%**였습니다. 이 짧은 측정으로 배터리 수명을 추정할 수는 없습니다.
- 표에 사용한 **유효 18회 모두** 저장 binding·즉시 노트 전환·다른 노트 보존·디스크 재로드·Unicode 삽입·Undo/Redo 검사를 통과했습니다. Crepe 실행은 DOM 체크박스 체크/해제도 통과했습니다.
- 최초 최종 배치의 마지막 Crepe 실행은 입력 단계에서 창이 보이지 않는 상태(`windowVisible=false`)로 프레임 대기가 실패했습니다. 해당 실행 전체를 제외하고 동일한 5만 자 조건을 재측정했습니다. 재측정에서는 양쪽 모두 통과했으며 표에는 부족했던 Crepe 1회만 추가했습니다.
- 로컬 원시 결과: `results/final-comparison/` 및 `results/large-retry/`. 이 결과 디렉터리는 생성물로 Git에서 제외됩니다.
- 웹 자산은 약 **4.1MiB**입니다. 비교 앱에는 동일한 실행 파일과 자산을 넣었으므로 두 비교 앱의 용량 차이가 제품의 용량 증가분을 뜻하지는 않습니다.

**판단:** 이 구성에서 가장 분명한 비용은 약 **90–170MiB의 메모리 증가**와 짧은 메모의 초기 준비 지연입니다. 반면 대기 CPU가 크게 증가한다는 증거는 없었습니다. 아래의 측정 범위와 실제 IME 검증을 함께 고려해야 합니다.

## 실행

이 디렉터리에서:

```sh
bash build.sh
open "apps/Editor Lab native.app"
open "apps/Editor Lab crepe.app"
```

macOS 14+, Swift, Node.js/npm이 필요합니다. 두 앱은 같은 Release 실행 파일을 사용하며 선택한 편집기만 생성합니다. 최초 빌드에는 npm/Swift 패키지 다운로드가 필요하고, **앱 실행은 오프라인**입니다. WebKit은 macOS 제공 프레임워크를 사용합니다.

- 두 창에서 같은 샘플 문서를 편집할 수 있습니다.
- `짧은 문서` / `1만 자` / `5만 자`: 노트 A에 해당 샘플을 로드합니다.
- `노트 A/B`: 같은 편집기 인스턴스를 재사용하여 노트를 전환합니다.
- `MD 저장`: 현재 편집 내용을 Markdown 파일로 내보냅니다.
- 실험용 노트는 메모리에 있으며 앱을 종료하면 초기화됩니다.
- Crepe 기본 기능을 사용합니다. 외부 Google Fonts 요청은 제거하고 시스템 폰트를 씁니다. CSS/JS/수식 폰트와 라이선스 고지를 앱에 포함합니다.

## 자동 비교

```sh
python3 compare.py
# 빠른 동작 확인 + 편집 영역 렌더링 캡처
python3 compare.py --repetitions 1 --sizes 1000 --capture
```

결과는 `results/<실행 시각>/`의 `summary.json`, 프로세스별 상세 리소스 JSON, 로그, 저장한 Markdown에 기록됩니다. `--output`으로 경로를 지정할 수 있습니다.

### 측정 조건

- 동일한 680×540 창, 16pt 본문 폰트, 동일한 Markdown 샘플.
- 짧은 샘플(실제 280 UTF-16), 약 1만/5만 UTF-16 문서. 긴 샘플은 여러 서식 문단으로 구성됩니다.
- 각 조건을 별도 프로세스로 3회 실행하며 native/crepe 순서를 교대합니다.
- 자동 측정 중에는 창을 floating 레벨로 표시합니다. 창이 가려지면 WebKit의 프레임 콜백이 중단될 수 있기 때문입니다. 일반 실행은 보통 창입니다. 웹 프레임 대기가 3초를 넘으면 실패를 기록합니다.
- OS 파일 캐시는 비우지 않습니다. 재부팅 직후의 cold start 측정이 아닙니다.
- 준비 후 3초 대기, **편집 영역에 포커스를 주지 않은 표시 상태에서** 6초간 대기 자원 사용을 측정합니다.
- `proc_pid_rusage`의 physical footprint, RSS, 누적 CPU 시간을 250ms 간격으로 수집합니다. CPU 100%는 코어 하나에 해당합니다.
- WebKit XPC 서비스는 부모가 launchd이므로 PPID만으로 합산하지 않습니다. 각 실행 직전에 없던 `com.apple.WebKit.*` 프로세스를 포함하고 PID/이름을 결과에 남깁니다. **비교 실행 중 다른 WebKit 앱을 새로 열지 않아야 합니다.** 프로세스 책임자 API로 검증한 귀속은 아닙니다.
- `idleFootprintMiB`는 대기 구간 합산 footprint의 중앙값입니다. RSS와 혼동하지 않습니다.

### 시간 지표의 범위

`firstReadyMS`는 앱 delegate 생성부터 편집 준비 신호까지입니다. 프로세스 생성 이전과 동적 라이브러리 로딩 시간은 제외됩니다.

- Native: SwiftUI wrapper의 문서 적용과 레이아웃 확인 후 AppKit display/transaction flush.
- Crepe: 로컬 페이지 및 편집기 생성 후 두 번의 `requestAnimationFrame`.

이 신호는 **실제 화면에 픽셀이 표시된 시각을 측정한 것이 아닙니다**. 웹 쪽에는 프레임 대기가 추가되므로 수 ms 차이로 우열을 판단하면 안 됩니다.

`syntheticEditMS`는 각각 `NSTextView.insertText`와 ProseMirror transaction을 통한 20회 삽입입니다. Native display flush와 웹 double-rAF라는 종료 조건 차이가 있어 **물리 키보드 입력 지연의 직접적인 A/B 수치로 사용하지 않습니다**. 처리량/중단 현상 확인용 원시 데이터입니다. 조합 입력기 테스트도 아닙니다.

## 동작 검증

자동 실행은 결과에 성공/실패를 기록하고 실패하면 non-zero로 종료합니다.

- 양쪽: 변경 binding 전달, 입력 직후 노트 전환·복귀, 이전 노트의 지연 알림이 도착할 때 다른 노트의 내용 보존, Markdown 디스크 저장·재로드, 한글/이모지 문자열 삽입, Undo/Redo.
- Crepe: 화면에 생성된 체크박스 DOM에 `pointerdown` 이벤트를 전달하여 체크 → 해제 검증. Markdown 문자열이나 체크 상태 명령을 직접 수정하지 않습니다.
- 실제 운영체제 마우스 입력·좌표 hit-test와 물리 한글 IME는 위 검사에 포함되지 않습니다.

직접 사용할 때에는 아래 순서로 비교하면 됩니다.

1. 체크박스를 반복 클릭하고 텍스트 선택과 섞어 보기.
2. `한글을 입력합니다`를 **한글 입력기로** 입력하며 조합 중 Backspace/방향키 사용하기.
3. 서식이 섞인 문장 일부 선택 → 굵게(Cmd+B) → 입력 → Undo/Redo.
4. 목록 끝에서 Enter/Tab/Shift+Tab, 다른 앱과 복사/붙여넣기.
5. 입력하자마자 노트 A/B 전환 → 복귀 → MD 저장 내용 확인.
6. 5만 자 샘플에서 스크롤·선택·입력 반응 확인.

## 해석과 다음 단계

이 시제품은 편집기 도입 비용을 분리해서 봅니다. NotchNotes의 노치 창 애니메이션, 자동 저장, 파일 선반, 앱 포커스 정책을 통합한 성능 결과는 아닙니다. 현재 앱 전용 `[[링크]]` / `![[이미지]]` 연결도 포함하지 않습니다.

Crepe는 Markdown을 파싱하고 재직렬화하므로 bullet 문자(`-` → `*`)나 끝 개행이 정규화됩니다. 원문의 바이트 보존을 요구하는 편집기와 다릅니다. 샘플에서는 기본 기능을 그대로 로드했으므로 기능별 번들/초기화 최적화 전의 비용입니다.

노트 전환 시 양쪽 모두 Undo 이력을 초기화합니다. 노트별 Undo/선택 상태 보존은 추가 통합 작업입니다. Crepe 변경 알림은 200ms debounce되므로, 노트 전환 전에는 `getMarkdown()`으로 현재 내용을 가져온 뒤 문서 ID를 바꿉니다. 지연 콜백의 Markdown이 현재 EditorState의 직렬화 결과와 같은지도 검사합니다.

실측 후 메모리/준비 시간 증가가 허용되는지 판단하고, 실제 한글 IME 및 노치 창 안에서의 포커스 동작까지 통과한 다음 본 앱 통합을 결정합니다.
